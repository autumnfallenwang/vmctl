# 0001 — Initial tech stack

- **Status:** accepted
- **Date:** 2026-07-22
- **Deciders:** project founder (captured during `/devkit-init`)

## Context

This is the founding stack decision for the project, recorded at scaffold time. It captures what we picked and why, so future contributors can understand the constraints in play when these choices were made.

vmctl streams and searches logs across the hosts of one deployment over SSH — the fallback for when logs are scattered across identical servers behind a load balancer and there is no Filebeat/Elastic pipeline to lean on. It has to be a command-line tool that is easy for both humans and AI agents to drive, and its output is JSON so agents can consume it directly.

Two constraints shaped the stack. First, the remote side is a locked-down standard RHEL environment where nothing may be installed, so all remote-side capability has to come from base utilities — this pushes complexity into the local tool rather than into anything deployed on the servers. Second, the tool itself must be installable into a plain `venv` via `pip` on environments that may not have uv. That rules out any dev tooling that leaks into the runtime and keeps packaging on standard PEP 621. Python was chosen as the implementation language; no deadline or team-size constraint was named.

## Decision

- **Primary language:** python
- **Package manager:** uv

- **Lint + format:** ruff — linter and formatter in a single tool.
- **Tests:** pytest.
- **Type checking:** pyright.
- **Packaging:** standard PEP 621 `pyproject.toml`, built to a wheel. uv is development-time only; the artifact installs with plain `pip` into a `venv`, and `uv export` can emit a pip-compatible `requirements.txt` for pip-only environments.
- **Config format:** YAML, defining named deployment profiles of hosts.
- **Output format:** JSON — an envelope adding source metadata around already-JSON ForgeRock log records.
- **Transport:** SSH with username/password authentication. The specific client (system `ssh` binary vs. `asyncssh` / `paramiko`) is deliberately left open — see `docs/architecture.md`.
- **No database, no server component, no frontend.**

## Consequences

**Positive**

- Python has mature SSH libraries (`asyncssh`, `paramiko`) and good async primitives for fanning out across hosts and merging streams, so the transport question can be settled later without re-picking the language.
- JSON in and JSON out means no parsing layer to build for ForgeRock logs, and the output is directly consumable by AI agents.
- ruff collapses lint and format into one fast tool; pyright pairs with the `pyright-lsp` plugin already enabled for this project, so editor intelligence and CI checks agree.
- Standard PEP 621 packaging keeps the door open to `pipx`/`pip` installs anywhere, including RHEL boxes with only a system Python.

**Negative / trade-offs**

- Python needs a runtime on whatever machine runs vmctl — no single static binary, unlike Go or Rust.
- uv for development but pip for deployment means two install paths to keep working; `uv.lock` has to be exported to `requirements.txt` for pip-only environments, and the two can drift.
- Doing all filtering locally (if that's where the split lands) means pulling more bytes over SSH than a remote-side `grep` would.

**Open risks**

- Password-based SSH constrains the client choice and complicates non-interactive use; credential rotation is the user's problem, so vmctl must fail clearly when a password goes stale.
- The remote no-install constraint means any capability gap in base RHEL utilities cannot be patched remotely — it has to be absorbed locally.
- The search query interface is undecided; picking it late risks reshaping the search path.
